# Bindings for other languages

kakemono is a Rust library; besides Python (`python/`), it is packaged for:

| Language | Package | Directory | How it calls Rust |
| --- | --- | --- | --- |
| JavaScript, TypeScript (Node.js, Bun) | `@kakemono/node` (npm) | `bindings/node/` | napi-rs 3, prebuilt for 8 platforms |
| JavaScript, TypeScript (browsers, workers, edge) | `@kakemono/wasm` (npm, experimental) | `bindings/wasm/` | wasm-bindgen |
| Java 17+, Kotlin | `io.github.iamcaominhtien:kakemono` (+ `kakemono-native`, `kakemono-langchain4j`) | `bindings/jvm/` | JNI |
| C#, F# (.NET 8+) | `Kakemono` (NuGet) | `bindings/dotnet/` | P/Invoke over the C ABI |
| C, C++ | `include/kakemono.h` + `kakemono_ffi` | `bindings/c/` | the C ABI itself |

Why these: [LANGUAGE-BINDINGS.md](LANGUAGE-BINDINGS.md) (in Vietnamese: the market survey and the
comparison with Kreuzberg). Other languages can call the command line.

Every binding has the same shape as the Python package: a `Document` is read and analysed once
(from bytes, a file, an `http(s)` address or an arXiv id), then written to any output: HTML (4
modes), Markdown, editable JSON, LaTeX, Typst, Word, EPUB, a PDF (Word documents, workbooks,
EPUB books, web pages), chunks for retrieval, or the document structure. The options have the
same names and defaults everywhere (camelCase: `imageDir`, `inlineImages`, `maxTokens`, ...), and a
wrong option is refused with its name (`imageDir does not apply to epub`). Each package's README
shows its API: [Node](../bindings/node/README.md), [WebAssembly](../bindings/wasm/README.md),
[JVM](../bindings/jvm/README.md), [.NET](../bindings/dotnet/README.md).

## Layout

```
bindings/                 a Cargo workspace of its own (not the root crate's)
  core/    kakemono-bindings   the façade: Document, OpenOptions, RenderOptions, Output, Error
  c/       kakemono-c          the C ABI (library kakemono_ffi), include/kakemono.h (cbindgen)
  node/    kakemono-node       napi-rs; index.js and index.d.ts are generated by `napi build`
  jvm/native/ kakemono-jni     JNI; jvm/ is the Maven project (Java API, LangChain4j, natives)
  wasm/    kakemono-wasm       its own workspace (wasm32 only, no default features)
  dotnet/                      C#, over the C ABI
```

`bindings/core` holds every check and default, so that the bindings stay thin; a new option goes
there first (`RenderOptions`, `Target::options`), then into each binding's typed options.

## Behaviour shared by every binding

- **Threads.** The work runs on a thread of kakemono's own with a 16 MB stack (`guarded` in
  `bindings/core`): reading a PDF recurses deeply, and the threads of a JVM, of .NET's pool or of
  libuv have about 1 MB. A `Document` can be written from several threads at once; closing it
  waits for the calls running on it. `jobs` (default: one per core) is per document: a server
  converting several documents at once should set it to 1 or 2.
- **Errors** have a kind: a wrong argument or option, a document that cannot be read or written
  so, or a bug of kakemono (a panic, caught: no panic crosses into the host; except in
  WebAssembly, where a panic aborts the module).
- **Fonts.** Laying out pages (a PDF of a Word document or a workbook, the hard modes of a Word
  document) needs a font: those installed, those embedded in the document, the folders of
  `KAKEMONO_FONT_DIRS`, or one given with `addFont` / `add_font` (WebAssembly has no other).
  Without any, those outputs fail with an error (Word's medium page is then the friendly one).
- **Cancellation** is not supported: a conversion runs to its end.

## Building and testing

```bash
cd bindings
cargo test --release -p kakemono-bindings -p kakemono-c       # the façade and the C ABI
(cd c && cbindgen --config cbindgen.toml --output include/kakemono.h)   # after changing the ABI
(cd node && npm ci && npx napi build --platform --release && npm test && npm run typecheck)
(cd wasm && ./build.sh && npm test)                           # needs wasm-bindgen-cli 0.2.130
cargo build --release -p kakemono-jni && mvn -f jvm/pom.xml verify
cargo build --release -p kakemono-c && dotnet test dotnet/Kakemono.sln
```

The `Bindings` workflow (`.github/workflows/bindings.yml`) runs these on every pull request.

## Releases

After each release (the `Release` workflow), the `Bindings` workflow builds the native libraries
for Linux (x86_64, arm64; glibc 2.17 and musl), macOS (x86_64, arm64) and Windows (x86_64, arm64),
sets every package's version from the tag (`scripts/set-bindings-version.py`), and assembles the
npm, Maven and NuGet packages (kept as workflow artifacts). It publishes them only when the
repository variable `BINDINGS_PUBLISH` is `true`, with these secrets:

| Registry | Secrets | Set up once |
| --- | --- | --- |
| npm | `NPM_TOKEN` (an automation token) | the `kakemono` organization on npmjs.com, for the `@kakemono/` scope |
| Maven Central | `MAVEN_CENTRAL_USERNAME`, `MAVEN_CENTRAL_PASSWORD` (a Central Portal token), `MAVEN_GPG_PRIVATE_KEY`, `MAVEN_GPG_PASSPHRASE` | the namespace `io.github.iamcaominhtien`, verified on central.sonatype.com; a GPG key published on a key server |
| NuGet | `NUGET_API_KEY` | the package id `Kakemono` on nuget.org |

A version already published is skipped, so the workflow can be run again by hand.
